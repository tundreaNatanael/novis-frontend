# novis-admin — the Novis admin console

The web app of [Novis](../novis-backend/README.md), a multi-tenant music-school ERP. It holds the
**admin console** that super-admins (platform owners) and organization admins use (organizations,
admins, teachers, students, courses, invites, freelance teachers, the lesson ledger, finance) and,
apart from it, the **teacher workspace** at `/teach` (D-051): every screen of the mobile app for a
teacher of a school or a freelance teacher — Today, Students, Calendar, Courses (freelance teachers
only: a school's admin creates its courses and assigns them, D-053), Profile and their sheets — laid out for a desktop, in English or Romanian. Students use the Novis app; a signed-in
account with neither an admin nor a teacher role sees a "Nothing to open yet" screen.

Desktop first, phone proper: the same features with layouts that adapt (tables become stacked
lists, forms become full-screen sheets).

## Setup

**Prerequisites**

- Node.js ≥ 22.22 (24 recommended) and npm.
- The backend running locally: follow [`../novis-backend/README.md`](../novis-backend/README.md)
  (Postgres in Docker, JDK 21, `./mvnw spring-boot:run` → `http://localhost:8080`).

**Backend settings the console needs** (backend `.env`):

| Key                    | Why                                                                                                                                                                                                                                                                                                         |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CORS_ALLOWED_ORIGINS` | must include this app's origin: `http://localhost:5173` in development, the console's production origin in production. Without it every request fails at preflight.                                                                                                                                         |
| `APP_BASE_URL`         | the app that serves invite and password-reset links. Today it points at the Expo app (`http://localhost:8081`), which also implements `/invite/:token` and `/reset-password/:token`; this console implements both routes too, so either can be the target ([gap G11](docs/BACKEND_GAPS.md#g11-deep-links)). |

**Environment** — copy `.env.example` to `.env`:

| Variable            | Default                 | Meaning                                 |
| ------------------- | ----------------------- | --------------------------------------- |
| `VITE_API_BASE_URL` | `http://localhost:8080` | Base URL of the API, no trailing slash. |

**Dev login**: the seeded platform owner `admin@novis.local` / `ChangeMe123!`. Logins are throttled
(5 per minute per email), so sign in once and let the console refresh its own session.

```bash
npm install
npm run start        # http://localhost:5173
```

## Session and auth behavior

- Tokens come from `POST /auth/login` (or `/auth/accept-invite`). The **access token** (≈15 min)
  lives in memory, mirrored per tab in `sessionStorage`; the **refresh token** (90 days, rotating)
  lives in `localStorage` under `novis-admin.refreshToken`. Both go through `src/auth/tokenStore.ts`,
  the one module to replace if a cookie / BFF approach is adopted later
  ([gap G12](docs/BACKEND_GAPS.md#g12-web-session-storage-and-cors)).
- A reload reuses the tab's access token; a new tab (or an expired access token) restores the
  session with one `POST /auth/refresh`, then `GET /users/me`. Refreshing on every load would race
  with token rotation and could sign the user out everywhere
  ([gap G17](docs/BACKEND_GAPS.md#g17-refresh-token-rotation-has-no-reuse-grace-window)).
- On `401 TOKEN_EXPIRED` the client runs **one** shared refresh (concurrent requests wait for it),
  stores **both** new tokens (refresh tokens rotate) and retries the requests once.
- `401 INVALID_REFRESH_TOKEN`, `ACCOUNT_UNAVAILABLE` or `INVALID_TOKEN`, or a rejected refresh,
  clear the session and send the user to `/login?reason=expired`.
- Signing out calls `POST /auth/logout` with the refresh token (best effort) and clears storage.
- Trade-off: a script injected into the page could read the refresh token. Mitigations: no
  third-party scripts, React's escaping, server-side reuse detection (reusing a rotated token
  revokes every session of the user), and the `tokenStore` seam.

## Known limitations

- Member lists sort by join date only and carry no account status (backend `Member` shape,
  [gap G14](docs/BACKEND_GAPS.md#g14-member-rows-carry-no-status-and-sort-only-by-membership-columns)).
- Only the freelance teachers list is searched by the server (`q`); the other big lists have no
  `q` parameter, so their search filters the loaded page and says so.
- Closed lessons cannot be reopened or re-assigned; the UI shows the supported transitions only
  ([gap G9](docs/BACKEND_GAPS.md#g9-change-any-information-on-lessons)).
- Lesson rows carry ids only; the ledger resolves teacher, student, course and organization names
  with one cached request per distinct id
  ([gap G19](docs/BACKEND_GAPS.md#g19-lesson-rows-carry-ids-only)).
- Finite weekly series (`POST /lessons/series`) are booked in the mobile app and the teacher
  workspace; the console books one lesson at a time or a permanent weekly lesson (D-054) and shows
  a lesson's series id only (D-045). An overlap's `409` does not say which lesson is in the way;
  a weekly lesson's dry run does, when the admin may open that lesson.
- A weekly lesson's "Next" date is computed from its start and interval; a date that was skipped
  still shows as next (the API lists no skipped dates), and Stop ends the rule today (no end date
  picker). "This and following" from a lesson's page is the teacher workspace's and the mobile
  app's; the console changes a rule from the student's page only.
- The lesson a homework refers to cannot be changed from the console: the edit sheet has no lesson
  picker (D-042). The checklist is replaced whole on save: two admins rewriting it at the same
  moment, the last save wins.
- The access token lives 15 minutes. A full page reload exactly while it is being refreshed can
  sign you out everywhere
  ([gap G17](docs/BACKEND_GAPS.md#g17-refresh-token-rotation-has-no-reuse-grace-window)).
- Every expired access token shows one `401` in the browser's network log before the silent
  refresh; it is the refresh protocol, not an error.
- Tables scroll sideways inside their card between 768 and 1023 px when the sidebar is expanded
  by hand; the icon rail (the default there) keeps every column in view.
- The Finance tab counts lessons, never money, and uses the browser's time zone for its periods
  (an organization has none). A student or teacher who left keeps a row; an org admin cannot open
  a former teacher's page from it ([gap G21](docs/BACKEND_GAPS.md#g21-a-teacher-who-left-has-no-page-for-the-organizations-admin)),
  and its link to a student who left (or whose account was deleted) opens "not found".
- The console cannot upload materials: teachers upload from the mobile app, and the console only
  opens uploaded files from the lesson page (D-050). An uploaded file shows as its title and file
  name with **Open**; nothing is previewed in the page itself.
- The teacher workspace uploads files only with `VITE_ENABLE_UPLOADS=true` and a storage
  provider on the backend (D-052). The browser sends the bytes to the bucket itself, so the bucket
  needs a CORS rule for the app's origin ([gap G22](docs/BACKEND_GAPS.md#g22-browser-uploads-need-a-cors-rule-on-the-bucket));
  without the flag, Attach material takes links only.
- The workspace's weeks start where the browser's language says (Monday for `ro-RO` and `en-GB`,
  Sunday for `en-US`), as the mobile app follows the device, whatever language is picked.
- `/teach` has Vitest flows but no Playwright coverage yet; the admin console's e2e specs are
  unchanged.
- Everything else that needs a backend change is tracked in [`docs/BACKEND_GAPS.md`](docs/BACKEND_GAPS.md).
